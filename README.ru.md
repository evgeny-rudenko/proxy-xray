## Постоянный Выход Через Амстердам

В этой экспериментальной ветке личный сервер в Амстердаме становится предпочтительной выходной точкой:
1. Амстердам напрямую.
2. Подписочный ретранслятор → Амстердам, если прямой доступ не работает.
3. Выход через подписку, если Амстердам недоступен через проверенные пути.
4. Если не работает ничего, зарубежный трафик блокируется; RU-маршрут остаётся прямым.

В `vless-extra.txt` находятся только транспорты Амстердама. Подписочные узлы используются как ретрансляторы или аварийные выходы. Пулы не смешиваются: все extra-транспорты и максимум три независимо проверенных подписочных узла, желательно на разных хостах.

Xray использует отдельные балансировщики `leastPing` и цепочку `dialerProxy`/loopback. Режим переключается через Routing API без перезапуска рабочего ядра. При изменении состава или конфигурации готовится временное ядро; оно заменяет рабочее только после проверки. Старые active/hot-пулы и кнопка Extra Pool удалены.

## Настройка

```sh
cp .env.example .env
cp vless-extra.example.txt vless-extra.txt
```

В `XRAY_SUB_URL` вставьте URL подписки от провайдера. В `vless-extra.txt` запишите по одной VLESS-ссылке на личный сервер Амстердама, сохранив TLS/Reality/gRPC/XHTTP-параметры.

Создайте `INBOUND_VLESS_ID` один раз:
```sh
python3 -c 'import uuid; print(uuid.uuid4())'
```
Это ваш пароль-UUID для подключения LAN-клиентов к гейтвею, а не UUID сервера из подписки. В клиенте указывается то же значение. LAN VLESS работает без TLS: открывать его в интернет нельзя.

Telegram необязателен:
- Создайте бота у **@BotFather**, вставьте HTTP API token в `TELEGRAM_BOT_TOKEN`.
- Напишите боту сообщение, приватно откройте `https://api.telegram.org/bot<TOKEN>/getUpdates` и возьмите `message.chat.id` для `TELEGRAM_CHAT_ID`. Не публикуйте URL и ответ.
- `TZ=Europe/Moscow` задаёт часовой пояс статистики.

```sh
docker compose config --quiet
docker compose up -d --build
```

## Порты И Подключение

| TCP-порт | Назначение |
| --- | --- |
| 1080 | SOCKS5 |
| 8123 | HTTP proxy, включая HTTPS CONNECT |
| 10086 | LAN VLESS |
| 18080 | Dashboard, диагностика, логи, QR |

HTTP-прокси в клиенте: `http://<LAN-IP-гейтвея>:8123`. В Firefox для SOCKS5 включите **Proxy DNS when using SOCKS v5**.
Откройте `http://<LAN-IP-гейтвея>:18080/client` или кнопку **QR**, чтобы получить строку и QR подключения. Через localhost получается адрес, непригодный для других устройств.

Опубликованы только эти порты. Xray API, контрольные порты и DNS-транспорт слушают loopback. Проброс публичного SOCKS UDP через TCP-переключатель не поддерживается.

## Переключение И DNS

Текущий маршрут проверяется каждые 20 секунд. Если первый контрольный сайт не ответил, проверяется второй. После двух неудачных циклов выбирается подтверждённый резервный путь. Для возврата с аварийного подписочного выхода на цепочку нужны три успешные проверки с интервалом 20 секунд и минимум 180 секунд после переключения. Возврат напрямую в Амстердам дополнительно требует пяти минут непрерывно успешных проверок балансируемого маршрута. Ошибка или разрыв между проверками больше 2,5 заданных интервалов (по умолчанию 50 секунд) обнуляют этот период. Разовые pinned-проверки отдельных транспортов не засчитываются в устойчивость прямого маршрута.

Если прямой Амстердам отказывает в первые три минуты после включения, следующая добровольная попытка возврата откладывается на 10 минут, а после повторного быстрого отказа — на 15 минут. Пять минут устойчивой работы уже активного прямого маршрута сбрасывают штраф. В обычном режиме реальный отказ текущего пути отменяет все ожидания: недавно проверенный прямой путь остаётся доступным для спасения связи. На старте первый разрешённый подтверждённый маршрут тоже включается без ожидания пяти минут. Dashboard показывает накопленную устойчивость и время до повторной попытки; рабочая цепочка не заменяется только из-за кратковременного успеха прямого пути.

Проверки закреплены за конкретными транспортами и парами. Для каждого транспорта цепочки выбор ретранслятора ограничен проверенными парами: доступность интернета через узел ещё не подтверждает его доступ к Амстердаму. Одни и те же три подписочных outbound используются без дополнительных копий. Отказ цепочки не штрафует исправный ретранслятор. Перед сообщением о недоступности Амстердама проверяются до двух независимых подписочных хостов и двух подходящих extra-транспортов. Это не доказательство аварии датацентра. Кандидаты тестируются последовательно с джиттером 120–300 секунд. Низкая скорость даёт предупреждение, а не немедленное переключение.

Split DNS используется и самим контейнером:
- RU-суффиксы разрешаются через прямые RU DNS; `geosite:category-ru` и `geoip:ru` маршрутизируются напрямую.
- Зарубежный DNS-over-TCP идёт через внутренний SOCKS-вход и выбранный зарубежный маршрут. Это правило применяется раньше RU-правил; прямого fallback нет.
- Bootstrap подписочных узлов и Амстердама не зависит от готовности выбранного выхода. Амстердам также разрешается через проверенный ретранслятор; TLS-имена сохраняются.
- Кэшированные ответы могут оставаться доступными. Новые зарубежные запросы без рабочего маршрута завершаются ошибкой.

Упавшее ядро перезапускается с задержкой 1–30 секунд и проверкой маршрута. TCP-сессии не переносятся между выходами и могут оборваться. Все extra-транспорты зависят от одного сервера. Цепочка добавляет задержку и расходует подписочный трафик; проверки и observatory также расходуют трафик.

## Dashboard И Состояние

Отображаются **выход и путь доставки**, выбранные Xray транспорты или UNKNOWN, выходной и ретрансляторный пулы, время проверок, причина переключения, ожидание возврата, скорость и квота подписки. Аварийный выход через подписку отмечается жёлтым: выходная точка изменилась.

Кнопка **«Перепроверить маршрут»** ставит последовательную проверку в очередь. Повторные нажатия объединяются. Она не закрепляет неработающий маршрут и не обходит защиту от частых переключений. Блоки обновляются без перезагрузки страницы.

В блоке **Exit and delivery path** есть переключатель режима:

- **Обычный**: прямой Амстердам → подписка → Амстердам → аварийный выход через подписку.
- **Subscription → Amsterdam**: цепочка с аварийным выходом через подписку при отказе Амстердама. Прямой Амстердам не выбирается, в том числе при рестарте и восстановлении ядра/конфигурации. Supervisor не проверяет прямой Амстердам; проверки ретрансляторов остаются последовательными. Native observatory Xray может продолжать проверять настроенные прямые транспорты, но эти проверки не разрешают пользовательский Direct-трафик.

Выбор сохраняется атомарно в приватном состоянии и переживает перезапуск. При ошибке записи режим не меняется. Отсутствующее/повреждённое состояние означает обычный режим, но зарубежный маршрут открывается только после проверки. Если все разрешённые пути отказали, зарубежный трафик и новые внешние DNS-запросы блокируются; RU остаётся напрямую. UI отдельно показывает выбранный режим, результат применения и фактический путь. Аварийный выход через подписку остаётся жёлтым. Переключатель не перезапускает Xray и не переносит TCP-сессии: для прекращения работы через старый путь переподключите клиент. Возврат в обычный режим не отменяет защиту возврата на Direct.

`POST /control/route-policy` принимает JSON `{"policy":"auto"}` или `{"policy":"subscription_only"}` и возвращает ID команды в очереди. Команды выполняются последовательно; несколько ожидающих изменений объединяются до последнего выбора. Запросы с постороннего Origin отклоняются, CORS не включён. `/json` содержит `route_policy` и `route_policy_command` отдельно от фактического `route_mode`. Web UI остаётся служебным интерфейсом локалки без авторизации: не открывайте его в интернет.

Страницы: `/`, `/json`, `/logs`, `/diagnostics`, `/diagnostics.json`, `/diagnostics/bundle`, `/servers/live`, `/servers/all`, `/client`. Диагностика показывает сохранённые проверки, не запускает параллельные запросы. Классический dashboard удалён.

Приватное состояние: `runtime/chain/state.json`. В нём кэш подписочных реквизитов и отдельная ограниченная история выходов, ретрансляторов и пар. Запись атомарная с синхронизацией; повреждённый файл откладывается в сторону. Старые успехи не разрешают включить маршрут после рестарта без новой проверки. Корневой `state.json` не изменяется. Не публикуйте `.env`, `vless-extra.txt`, `state.json`, `runtime/` и сгенерированные QR.

## Настройки И Проверки

`docker compose run --rm proxy-xray --help` показывает поддерживаемые параметры. По умолчанию: `--relay-pool-size 3`, `--check-interval 20`, `--max-failures 2`, `--return-successes 3`, `--return-hold 180`, `--direct-return-stable 300`, `--direct-retry-delay 600`, `--direct-retry-max 900`, `--direct-failure-window 180`, джиттер кандидатов 120–300 секунд, обновление подписки раз в 7200 секунд. Таймеры защиты от возвратов живут в памяти supervisor и сбрасываются при его перезапуске; на каждом старте маршруты заново проверяются. После старта из кэша/extra подписка повторно запрашивается через 30 секунд. Старые параметры смешанных пулов и `DNS_GLOBAL_ROUTE` больше не поддерживаются.

```sh
python3 -m unittest discover -s tests
bash -n run.sh scripts/deploy-server.sh tests/client-smoke.sh
docker compose config --quiet
docker run --rm --network none --entrypoint python3 \
  -v "$PWD/proxy_xray:/proxy_xray:ro" -v "$PWD/tests:/tests:ro" \
  proxy-xray:local /tests/chain-integration.py
docker compose logs --tail 100
```

Изолированные тесты работают с вымышленными VLESS-серверами без доступа в интернет. Loopback разрешён только на тестовых серверах, рабочие ограничения не ослаблены. Дополнительная реальная проверка сравнивает выходной IPv4 напрямую и через два ретранслятора, не выводя IP и ключи:
```sh
docker compose exec -T proxy-xray python3 - < scripts/check-chain-live.py
```

Ветка тестируется локально. Автоматической выкатки на домашний сервер нет. Несколько часов эксплуатационного наблюдения остаются отдельным этапом приёмки.
